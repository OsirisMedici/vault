# Agent Vault fit assessment for Vault

Researched 22 October 2026. This is a source review, not runtime or security acceptance. Only this document was written. No services, installations, secrets, upstream checkout, or Karen source were used.

## Recommendation and intended outcome

Evaluate Infisical Agent Vault as a separate broker for narrowly scoped API access. Keep Vault's protected website-login work separate. Do not copy its credential storage, cryptography, or proxy core into Vault to solve the current GoDaddy browser-login requirement.

Osiris's current outcome is account selection, private approval/unlock, protected fill in the intended T3 tab, and verification of the exact signed-in identity. Passwords and sessions must stay outside ordinary tool results and model context. The local MCP connector already represents that contract with bounded commands and responses, but its native browser adapter remains pending. Agent Vault addresses HTTP credential injection; the reviewed sources do not establish that protected browser workflow. See [Vault outcome](plans/agent-access-outcome-2026-10-22.md), [connector status](../integrations/vault-mcp/README.md), and [response projection](../integrations/vault-mcp/src/bridge.mjs).

For an API pilot, success would mean an agent can perform one authorized operation using a short-lived broker token, cannot read the stored credential, cannot reach unauthorized destinations, and receives only approved output. The user would approve access privately, then see useful results and bounded failures. API access would still require authorization for the actual operation. Website login, native Touch ID, Bitwarden enrollment, browser session transfer, and installed-app replacement are excluded from that pilot.

## Credential injection and scoping

**Documented.** Agent Vault is a separate server/CLI with a management API and an authenticated forward proxy. Clients use proxy settings and trust its CA. The broker resolves credentials and attaches them when forwarding requests. Its service rules support bearer, HTTP Basic, API-key, custom headers, and passthrough. Explicit placeholder substitutions also support path, query, headers, request bodies, and client-to-server WebSocket text. JSON and URL-encoded form bodies receive content-specific escaping; multipart and compressed bodies are skipped. Sources: [architecture and usage](https://github.com/Infisical/agent-vault/blob/d5836ec3bb2315de38043d742ae5daca11a4944a/README.md), [service configuration](https://github.com/Infisical/agent-vault/blob/d5836ec3bb2315de38043d742ae5daca11a4944a/docs/learn/services.mdx#L46-L251), [substitution implementation](https://github.com/Infisical/agent-vault/blob/d5836ec3bb2315de38043d742ae5daca11a4944a/internal/brokercore/substitution.go#L36-L149).

**Code observation.** Credential injection matches host, optional port, and path. The service model has no HTTP-method or request-field authorization predicate. A rule allowing one API path can therefore permit several operations at that path. A host without an explicit port matches any port. Unmatched traffic passes through by default; `unmatched_host_policy=deny` must be selected for an allowlist. Sources: [service model](https://github.com/Infisical/agent-vault/blob/d5836ec3bb2315de38043d742ae5daca11a4944a/internal/broker/broker.go#L21-L38), [matching semantics](https://github.com/Infisical/agent-vault/blob/d5836ec3bb2315de38043d742ae5daca11a4944a/docs/learn/services.mdx#L259-L293), [unmatched policy enforcement](https://github.com/Infisical/agent-vault/blob/d5836ec3bb2315de38043d742ae5daca11a4944a/internal/brokercore/credential.go#L108-L156).

**Documented and code-confirmed.** Use instance role `no-access` with only the required vault grant. Vault `proxy` callers cannot reveal credentials. Members and admins can reveal them, including through the HTTP API. The scoped-session endpoint requires a member-or-higher caller and currently issues only `proxy` sessions. Scoped sessions are vault-bound, with documented TTL bounds of five minutes to seven days, defaulting to 24 hours. Long-lived agent tokens have no expiry and may have grants in multiple vaults. Sources: [roles](https://github.com/Infisical/agent-vault/blob/d5836ec3bb2315de38043d742ae5daca11a4944a/docs/learn/permissions.mdx#L10-L63), [session creation](https://github.com/Infisical/agent-vault/blob/d5836ec3bb2315de38043d742ae5daca11a4944a/internal/server/handle_sessions.go#L71-L171), [reveal authorization](https://github.com/Infisical/agent-vault/blob/d5836ec3bb2315de38043d742ae5daca11a4944a/internal/server/handle_credentials.go#L109-L168), [token lifetimes](https://github.com/Infisical/agent-vault/blob/d5836ec3bb2315de38043d742ae5daca11a4944a/docs/learn/security.mdx#L66-L78).

**Assessment.** Scoping is primarily per vault and service. Create separate vaults when agents must receive different service sets. Keep privileged token minting in a trusted controller. Broker tokens remain usable capabilities that agents can steal or misuse, even when underlying API keys are hidden. Proposal approval authorizes configuration changes, not every subsequent API action. Vault still needs its own operation approval rules and provider-side least privilege. Source: [proposal semantics](https://github.com/Infisical/agent-vault/blob/d5836ec3bb2315de38043d742ae5daca11a4944a/docs/learn/proposals.mdx#L6-L43).

## Security boundaries and limitations

### Responses can return secrets

**Code observation.** The HTTP response path copies upstream headers except its strip list, then streams the response body to the caller with `io.Copy`. The strip list removes hop-by-hop headers and `Set-Cookie`; it is not a general secret filter. Sources: [response forwarding](https://github.com/Infisical/agent-vault/blob/d5836ec3bb2315de38043d742ae5daca11a4944a/internal/mitm/forward.go#L375-L426), [response header filter](https://github.com/Infisical/agent-vault/blob/d5836ec3bb2315de38043d742ae5daca11a4944a/internal/brokercore/brokercore.go#L152-L158).

**Assessment.** An allowed upstream that echoes an injected header or substituted body can return the real value to the agent. Other response headers, HTML, error pages, downloaded content, or token-issuing endpoints can also disclose credentials or sessions. Encoding a value does not make it safe. Restricting substitutions to a request component does not constrain what upstream returns. This is a source-derived risk, not a reproduced exploit or a claim about a particular provider.

The security page's opening non-disclosure statement needs qualification. Its own later table acknowledges authorized credential reveal, and the proxy code does not enforce response non-disclosure. Treat the guarantee as keeping stored credentials out of ordinary proxy-role retrieval and outbound client construction, subject to trusted upstream behavior and isolation. Source: [security statement and sensitive-data table](https://github.com/Infisical/agent-vault/blob/d5836ec3bb2315de38043d742ae5daca11a4944a/docs/learn/security.mdx).

For Vault's stricter output contract, prefer named action adapters that constrain request fields and reconstruct an approved response schema. Exclude reflection, debugging, credential-reading, and token-issuing routes unless a trusted adapter contains their output. Generic string redaction would not prove the absence of transformed secrets or newly minted tokens.

### Same-host execution requires real isolation

**Documented.** The README recommends a separate host for the broker. Default host-mode wrapping sets environment variables; an agent can bypass them and retain its existing filesystem and network access. A wrapper does not isolate broker storage, process memory, operator sessions, or unrelated local credentials from an unrestricted same-user agent. Sources: [deployment boundary](https://github.com/Infisical/agent-vault/blob/d5836ec3bb2315de38043d742ae5daca11a4944a/README.md#basic-usage), [host-mode warning](https://github.com/Infisical/agent-vault/blob/d5836ec3bb2315de38043d742ae5daca11a4944a/docs/agents/overview.mdx#L8-L23).

The pinned revision also has opt-in Docker isolation with firewall-controlled egress and restricted mounts. This is newer than the overview's statement that stronger local isolation is on the roadmap. Its detailed guide excludes container escapes and exfiltration through permitted upstreams. `--no-firewall` removes network enforcement. On macOS, `--share-agent-dir` can extract the Claude Code credential from Keychain into a filesystem file; do not use that convenience path for this evaluation. Source: [container modes, mounts, macOS bridge, and threat model](https://github.com/Infisical/agent-vault/blob/d5836ec3bb2315de38043d742ae5daca11a4944a/docs/guides/container-isolation.mdx).

**Assessment.** Container mode is meaningful isolation to test, not evidence that the current unrestricted T3 session is protected. Keep broker state, administration credentials, Docker control, and personal home directories outside the agent's reach. The local Vault connector similarly documents that socket permissions are a same-user boundary, not protection against unrestricted same-user access.

### TLS interception changes the trust model

**Code observation.** CONNECT terminates TLS at Agent Vault using certificates minted by its CA. The broker makes a separate upstream connection with TLS verification. This is intentional interception; traffic is readable by the broker. It is not cryptographic end-to-end confidentiality between the agent and destination. Sources: [TLS termination](https://github.com/Infisical/agent-vault/blob/d5836ec3bb2315de38043d742ae5daca11a4944a/internal/mitm/connect.go#L46-L155), [upstream TLS transport](https://github.com/Infisical/agent-vault/blob/d5836ec3bb2315de38043d742ae5daca11a4944a/internal/mitm/proxy.go#L80-L91).

The proxy listener itself uses HTTP, so its bearer capability in `Proxy-Authorization` is exposed on that outer hop without a protected network or tunnel. Also, the code supports plain HTTP upstreams and performs the same injection there. Do not rely on the security page's blanket HTTPS wording. Use an encrypted private network, HTTPS destinations, explicit ports, and separately hardened management access. Certificate pinning or clients that ignore proxy/CA settings may be incompatible; that remains a compatibility test. Sources: [proxy transport](https://github.com/Infisical/agent-vault/blob/d5836ec3bb2315de38043d742ae5daca11a4944a/internal/mitm/proxy.go#L151-L160), [HTTP forwarding and injection](https://github.com/Infisical/agent-vault/blob/d5836ec3bb2315de38043d742ae5daca11a4944a/internal/mitm/forward.go#L78-L145), [shared request path](https://github.com/Infisical/agent-vault/blob/d5836ec3bb2315de38043d742ae5daca11a4944a/internal/mitm/forward.go#L184-L261).

### Storage, logging, and revocation need operational checks

The documented store uses AES-256-GCM with a random data key, optionally wrapped using a password-derived key. Passwordless mode stores the data key unencrypted in the database. This is not Bitwarden's end-to-end encrypted human-vault model. The running broker must be trusted with plaintext. The implementation also converts decrypted credentials to Go strings, so the security page's broad statement about never converting sensitive slices to strings should not be repeated as a guarantee. Sources: [key management](https://github.com/Infisical/agent-vault/blob/d5836ec3bb2315de38043d742ae5daca11a4944a/docs/learn/security.mdx#L23-L54), [decryption and string caching](https://github.com/Infisical/agent-vault/blob/d5836ec3bb2315de38043d742ae5daca11a4944a/internal/brokercore/credential.go#L168-L207).

Structured proxy logs omit bodies, header values, and query strings, but retain paths and identifying metadata. That is useful hygiene, not protection for secrets an agent already embeds in a path or for upstream/application logs. Source: [event fields](https://github.com/Infisical/agent-vault/blob/d5836ec3bb2315de38043d742ae5daca11a4944a/internal/brokercore/logging.go#L27-L47).

Authentication is resolved once per CONNECT tunnel and reused by its handler. Do not promise immediate expiry or revocation on existing connections without testing keep-alive tunnels and WebSockets. Sources: [CONNECT authentication](https://github.com/Infisical/agent-vault/blob/d5836ec3bb2315de38043d742ae5daca11a4944a/internal/mitm/connect.go#L74-L87), [captured request scope](https://github.com/Infisical/agent-vault/blob/d5836ec3bb2315de38043d742ae5daca11a4944a/internal/mitm/forward.go#L173-L181).

## Browser form-login fit

**Assessment: unsuitable as the direct solution to the first GoDaddy acceptance.** HTTP Basic authentication is not HTML form filling. Body substitution could place a placeholder into a simple form POST, but the reviewed code does not supply account selection, tab/thread binding, private native approval, DOM/provider adapters, MFA/passkey handling, session handoff, or exact destination identity verification.

More decisively, response filtering strips `Set-Cookie`, so a browser cannot acquire the normal session cookie through that response path. Tokens embedded in response bodies would instead pass through to the caller. OAuth support stores and refreshes API tokens; it does not demonstrate a signed-in website session. Sources: [cookie stripping](https://github.com/Infisical/agent-vault/blob/d5836ec3bb2315de38043d742ae5daca11a4944a/internal/brokercore/brokercore.go#L152-L158), [OAuth credential workflow](https://github.com/Infisical/agent-vault/blob/d5836ec3bb2315de38043d742ae5daca11a4944a/docs/learn/credentials.mdx#L33-L59).

The SDK configures spawned clients with proxy and CA environment settings. This does not establish control over the network stack of an already-running T3 preview tab. Adding browser proxy support, cookie handling, and private session ownership would be new integration work and would need a fresh security review. Source: [SDK integration contract](https://github.com/Infisical/agent-vault/blob/d5836ec3bb2315de38043d742ae5daca11a4944a/sdks/sdk-typescript/README.md#L13-L49).

## Integration choice and handoff

Prefer an external broker accessed through its supported CLI/API/TypeScript SDK, with a small Vault-owned action adapter where needed. This keeps upstream patches reviewable and avoids inheriting maintenance of a second cryptographic store and MITM implementation. Its core packages live under Go `internal/`, and its broker core depends on storage and crypto packages; copying a helper would not extract a self-contained security product. Source: [core dependencies](https://github.com/Infisical/agent-vault/blob/d5836ec3bb2315de38043d742ae5daca11a4944a/internal/brokercore/brokercore.go#L1-L17).

There is no documented Vaultwarden backend in the reviewed credential-store design. It offers built-in storage and Infisical-backed synchronization. The latter caches encrypted credentials locally and continues serving the last snapshot on sync failure without an automatic fail-closed window. A Vaultwarden adapter would be new work with unlock, caching, revocation, and ownership implications. Do not export the human vault into this service for convenience. Source: [credential stores and outage behavior](https://github.com/Infisical/agent-vault/blob/d5836ec3bb2315de38043d742ae5daca11a4944a/docs/learn/credential-stores.mdx).

The parent owns any external temporary checkout and dummy-only tests. Suggested acceptance cases, with no real credentials:

1. Pin `d5836ec3bb2315de38043d742ae5daca11a4944a`. Record the artifact, configuration, and test environment separately from source claims.
2. Inject a dummy header and body placeholder into a controlled endpoint. Verify the agent starts with placeholders and a proxy token only.
3. Make the controlled endpoint echo the injected value in a body and a response header. Record whether it reaches the client. Check `Set-Cookie` separately. Never use a public echo service with real credentials.
4. Verify strict unmatched-host denial, exact host/port/path matching, forbidden credential reveal, cross-vault rejection, and rejection of session minting by a proxy caller.
5. Exercise multiple HTTP methods on the same allowed path to expose the operation-authorization gap.
6. Test expiry and revocation both on a new connection and an already-open CONNECT/WebSocket connection. Measure the actual cutoff.
7. In a separately authorized isolation test, attempt direct egress and DNS bypass with proxy environment variables removed. Report host mode and container mode separately.
8. Check upstream certificate validation, untrusted CA rejection, and whether HTTP upstream requests can receive dummy credentials. Keep trust changes confined to the disposable test client.
9. Inspect dummy logs and cold-restart behavior. If testing Infisical-backed storage later, include stale-cache and disconnect behavior.

This report supports a bounded API experiment. It does not accept Agent Vault as Vault's password-manager backend, establish a safe arbitrary-response channel, or complete GoDaddy sign-in. The existing native browser-login owners retain that work; no Karen changes or real-account acceptance occurred here.
